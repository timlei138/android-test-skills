# android-gui-testing 质量进阶计划：A- → A+

> 来源：2026-09-09 全量代码评审（三轮核销后基线 = A-，全部严重/中等问题已清零）。
> 本文档是「从优秀到卓越」的能力建设规划，按价值/成本排序，分四个阶段。
> 注意：涉及 `framework/`、`SKILL.md`、`docs/` 的改动仍受变更管控约束，
> 每项实施前先出「原文 vs 修改后」提案经人确认。

---

## 现状基线

- 单用例执行器 + 知识工程已打磨到 A-：分层边界严格执行、结果语义机器可消费、
  105 单测全绿、证据链完整、多副本漂移可检测。
- 核心缺口不是 bug，而是三块体系能力：
  1. 从「用例」到「套件」（runner + 质量信号）
  2. 从「代码测试」到「Agent 行为测试」（eval 回路）
  3. 从「能装上」到「可交付」（版本钉 + CI + smoke）

---

## 阶段一：质量信号层（价值最大、成本最低，数据全在 SQLite 里）

### 1.1 Flakiness 聚合视图

- **做什么**：Web UI 记录列表加「近 N 次通过率」列；用例详情加历史趋势
  （final_status 时间线、耗时、dump 次数）。同一 `script_path` 的多次执行
  group by 即可得出。
- **为什么**：GUI 测试的头号敌人是用例悄悄烂掉。没有通过率趋势，
  「时通时不通」只能靠人肉记忆发现。
- **验收**：任意用例能看到近 10 次执行记录与通过率；flaky（通过率在
  20%~80% 之间）用例在列表页有醒目标记。

### 1.2 套件级 runner

- **做什么**：新增 `run_suite.py`（或 `run_case.py --all`）：批量执行
  `cases/<包名>/` 全量用例 → 套件聚合报告（Markdown + DB suite 表）→
  套件级退出码（任一 FAIL 即非零）。串行先行，多设备分片并行作为后续项。
- **为什么**：现在回归靠逐个敲命令，套件语义（整体通过/失败/耗时）不存在。
- **验收**：一条命令跑完整个 cases/ 树；产出套件报告含每用例结论/耗时/报告链接；
  单用例失败不中断后续用例（隔离执行，子进程模式）。

### 1.3 环境漂移检测

- **做什么**：用例开始快照、结束 diff：rotation / stayon / 已授权运行时权限 /
  前台包 / 勿扰等系统设置。漂移 → 自动 WARN「用例污染了设备环境」。
- **为什么**：现在防污染靠约定与注释（119 旋屏教训），机器化后约定变断言。
  可沉淀为 `framework/states.py` 的通用能力（环境快照/比对是跨 App 通用的）。
- **验收**：故意写一个改 rotation 不恢复的用例，跑完报告里出现环境漂移 WARN。

## 阶段二：Agent 行为评测回路（Agent Skill 的 A+ 门槛）

### 2.1 生成质量 eval 集

- **做什么**：小型离线 eval：固定 probes 缓存（storage/probes 已有）+
  3-5 组标准用例输入（口述文本）→ 离线重放用例生成流程 →
  断言生成脚本符合硬规则：
  - App 自有控件用 rid 定位（不出现裸坐标/tap_xy 写死值）
  - 含 `USER_INPUT` 常量
  - 命中标准链路时复用 `_flow.py`（不重新探路）
  - 断言引用的动态文案能在探索记录中找到出处
- **为什么**：SKILL.md 是系统灵魂但零回归保障。改一行提示词/知识卡，
  靠什么证明 Agent 行为没退化？tests/ 只测框架代码不测 Agent 契约。
- **验收**：eval 可离线运行（不连设备、不调真模型可用录制回放）；
  修改 SKILL.md 核心原则后 eval 能捕到至少一类违规行为。

### 2.2 上下文预算门禁

- **做什么**：CI 脚本统计常驻上下文体量：SKILL.md、_system.md、各知识卡的
  行数/估算 token，超预算即红（预算值写死在脚本里，如 SKILL.md ≤ 250 行）。
- **为什么**：懒加载/子文档拆分的 token 经济设计没有量化防线；
  知识卡有 GC 机制但靠人记得触发，度量才自动。
- **验收**：人为把某卡撑到预算 2 倍，CI 报红并指出是哪个文件。

### 2.3 知识卡新鲜度追踪

- **做什么**：用例执行时框架顺手记录「本次命中知识卡 = 前台包名」入 DB；
  Web UI 知识库页展示「该卡最近被通过用例验证的时间」；
  超阈值（如 30 天）未验证的卡列出来。
- **为什么**：「最近验证」行是散文，机器不可消费；知识腐化现在要等
  大版本回归才暴露。
- **验收**：DB 能查出每张卡的最后验证时间；界面或命令行能列出「过期卡清单」。

## 阶段三：交付工程化

### 3.1 依赖钉版本

- **做什么**：新增 `requirements.txt`（uiautomator2 / rapidocr_onnxruntime /
  Pillow 精确版本），`setup.sh` / `setup.ps1` 改为 `pip install -r`。
- **为什么**：框架注释里全是「实测行为」，对上游行为漂移最敏感；
  滚动版本 = 团队基线静默漂移。
- **验收**：干净机器 setup 后 `pip freeze` 与 requirements 一致。

### 3.2 版本标识 + CI

- **做什么**：
  - `framework/VERSION` 文件，`run_case.py` 启动时打印（多副本漂移检测更硬）；
  - GitHub Actions（或等价 CI）：push 触发 `python -m unittest discover -s tests`；
  - `export.sh` 打包时注入版本号。
- **为什么**：分发出去的包无法回答「这是哪个版本」；单测靠人记得跑。
- **验收**：CI 红绿可查；任意安装副本能报出自己的版本。

### 3.3 安装后 smoke 用例

- **做什么**：`setup.sh` 末尾可选跑一个 10 秒 smoke（连设备 dump + 截图 +
  出报告 + 入库，用 PROBE_ 前缀不入库即清）。
- **为什么**：import 自检验证不了设备全链路；「装完但跑不起来」的排障成本归零。
- **验收**：全新环境 setup 后 smoke 通过 = 可直接跑正式用例。

### 3.4 Web UI 绑定地址防护

- **做什么**：启动时若绑定非 127.0.0.1 地址，打印醒目警告
  （本服务可删记录/存 API key/编辑知识卡）。
- **验收**：`--host 0.0.0.0` 启动时日志出现安全警告。

## 实施顺序建议

```
阶段一（1.1 → 1.2 → 1.3）   ← 数据都在库里，纯增量，不动现有契约
    ↓
阶段三（3.1 → 3.2 → 3.3 → 3.4） ← 交付底线，互相独立可并行
    ↓
阶段二（2.2 → 2.3 → 2.1）   ← eval 集最重，放最后做深
    ↓
阶段四                        ← 穿插在以上各阶段顺手清
```

## 不做清单（明确排除，防范围蔓延）

- 自研录制回放工具（probe/trace 机制已覆盖该价值）
- 跨平台（iOS）扩展（架构上预留了分层，但不在本期目标）
- 视觉模型自训练/微调（路由层已支持切换，模型选型是运维问题不是框架问题）
