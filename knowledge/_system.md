# 通用系统界面（权限弹窗 / 系统对话框）—— 兜底卡

<!-- 本卡是前台包名不在任何 App 卡时的兜底参考（AI 主动检索加载，非框架自动注入）。机器只阅读，不 parse。 -->

- **app**: `_system`（兜底卡，不可删除）
- 适用包名: `com.android.permissioncontroller`、`com.google.android.permissioncontroller`、`com.android.systemui`、`android`

## 界面结构

- 权限弹窗: 通常有「允许 / 拒绝」或「仅在使用中允许 / 始终允许」按钮
- 系统对话框: 确认 / 取消按钮
- Android14+ 照片权限: 按钮为「选择照片」/「全部允许」（不是普通「允许」）

## 运行时权限弹窗（跨 App 通用，写权限用例前必读）

### 弹窗出现 = 权限未授予

已授予则**不弹**，直接进入目标功能（相机 / 选择器等）；未授予才弹。
所以"看到权限弹窗"本身就是"该权限尚未授予"的判定依据。

### 按钮文案会随「是否拒绝过」变化（注意：2026-09-02 Android 17 实测）

| 权限 | 首次请求 | 拒绝过一次后再请求 |
|---|---|---|
| CAMERA | 仅在使用时允许 / 仅本次使用时允许 / **拒绝** | 仅在使用时允许 / 仅本次使用时允许 / **拒绝并不再询问** |
| MEDIA（照片/视频） | 选择照片 / 全部允许 / **拒绝** | 选择照片 / 全部允许 / **拒绝并不再询问** |
| 普通危险权限（位置/通讯录/麦克风等） | 仅在使用中允许 / 仅本次允许 / 拒绝 | 同类地变为「拒绝并不再询问」 |

**「拒绝」→「拒绝并不再询问」是系统通用行为，不限于日历。**

### 因此：一律用正则点击，不要用 tap_text 精确匹配

`t.tap_text("拒绝")` 是精确匹配，第二轮起必然失配 —— 用例表现为**时通时不通**，
很容易被误判成"时序/等待不够"而白白排查很久。改用框架通用能力 `tap_text_re()`：

```python
t.tap_text_re(r"^拒绝(并不再询问)?$")                                  # 拒绝类
t.tap_text_re(r"^(仅在使用时允许|仅本次使用时允许|全部允许|选择照片|允许)$")  # 允许类
```

看门狗（`start_watchdog`）不受影响：其词表已内置「拒绝并不再询问」，
且按 `text="..."` 精确匹配，两个词互不误命中。

### 用例排布：先拒绝、后允许，按权限分组

同一权限的两条路径**连续测完再换下一个权限**，且组内**先测拒绝**：

```
CAMERA: 拒绝 → 允许      MEDIA: 拒绝 → 允许
```

理由：拒绝会改变弹窗形态，先拒绝能让"允许"路径落在确定的第二形态上；
按权限分组则同一权限的两条路径共用一次导航，少一半导航开销。

### 重置前提

- `pm revoke <pkg> <权限>` 后系统弹窗**仍会再弹**（权限 flags 只带 `USER_SET`，
  **不是** `USER_FIXED`），可用于重置"未授予"前提
- 但重置后按钮已是「拒绝并不再询问」形态 → 仍需正则匹配
- `pm clear <pkg>` 一并重置全部权限与数据（最干净）

## 高效操作

- 权限弹窗: 按测试用例预期点「允许」或「拒绝」（一般点允许；Android14+ 照片权限点「全部允许」）
- 确认对话框: 点确认/确定继续，点取消/拒绝放弃
- 运行时权限弹窗约 8 秒自动消失：出现必须立即点击（框架看门狗 `start_watchdog()` 检测即点）
- 权限处理策略: `policy="allow"` 点同意/允许/全部允许；`policy="deny"` 点拒绝/禁止 —— 同一套逻辑验证同意与拒绝路径
- 点权限按钮用 `tap_text_re()` 正则（见上），不要用 `tap_text()`

## 预装 APP 的卸载与恢复（跨 App 通用，卸载/恢复类用例前必读）

### 恢复预装应用：固定路径

- **固定路径**：`设置 → 应用管理 → 恢复预装应用 → 找到目标 APP → 恢复`
  这是恢复预装 APP 的**唯一固定入口**，不要另找路径、也不要用命令替代。
- 判定恢复成功：APP 重新出现在桌面「所有应用」列表，且该页按钮由「恢复」变为「打开」。
- 注意：`pm install-existing <pkg>` 对**已真正卸载**的预装包**无效**
  （实测：`PackageManager$NameNotFoundException: Package com.zui.calendar doesn't exist`）。
  它只能重新启用"被禁用"的包；被完整移除的包必须走上面的「恢复预装应用」UI。

### 判断一个 APP 是否支持卸载

- 判定依据：**Launcher 桌面 / 所有应用列表长按该 APP 图标**，看弹出菜单里**有没有「卸载」**：
  - 有「卸载」→ 支持卸载（实测：便签、日历 均有）
  - **没有「卸载」→ 该 APP 不支持卸载**（实测：系统应用「设置」菜单只有 小部件 / 应用信息）
- 不要用"`pm uninstall` 是否返回 Success"来判定用户侧可卸载性：
  系统预装包 `pm uninstall` 常返回 Success，但那是另一套语义，
  与桌面长按是否提供卸载入口并不一致。
- 长按菜单必须用 uiautomator2 原生 `long_click()` 触发；
  `input swipe x y x y <ms>` 模拟长按**经常弹不出菜单**（详见 `com.zui.launcher.md`）。

### 判定"包是否安装"必须精确匹配（真实事故坑）

- `pm list packages <pkg>` 是**子串匹配**：查 `com.zui.calendar` 会同时命中
  `com.zui.calendar.overlay.*` 等主题/覆盖包，导致**永远认为已安装**。
- 必须按行精确匹配：

  ```python
  def exact_installed(t):
      o = t.adb_shell("pm", "list", "packages", PKG)
      return ("package:" + PKG) in [l.strip() for l in o.splitlines()]
  ```

- 事故后果：误判"已安装"会让卸载检测恒为 False、`finally` 里的兜底恢复永不触发，
  最终把设备留在"APP 已卸载、桌面图标消失"的状态。
  凡是带销毁性的卸载用例，`finally` 兜底必须走「恢复预装应用」UI + 精确匹配校验。

## 验证要点

- 点击后弹窗应消失，界面回到原应用
- 验证「进入某界面」用前台 Activity 判定（`current_activity()`），不要用界面文字猜测
